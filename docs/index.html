Project

kvstore

It is a small server that remembers labelled pieces of text and hands any one of them straight back when a program asks for it.

For the developer whose app keeps asking the database the same question over and over.

Real Go code, built 2026-07-27, commit fd71c7f

The database keeps answering the same question

It is Tuesday afternoon and one page on your site has gone slow. You open the log and find the same lookup on every single visit: fetch this customer's display name. The name has not changed in weeks. The database is asked again anyway, and every visitor waits while the answer comes off a disk.

kvstore is the thing you put in front of that question. It holds the answer in memory, ready, and hands it back without touching a disk at all.

If you opened this file by double clicking it, the prompt stays inactive: browsers refuse to load compiled code from a local file. Open the published page, or serve this folder over http, and it comes alive. Either way a session captured from the real server is shown instead.

One part is missing on purpose. A browser tab has no network sockets, so the piece that listens for connections is not here. What runs in your tab is the storage code and the command reader, exactly as they are in the repository. The listener, and the one small worker it starts per visitor, only exist when you run the real program on a machine.

Nothing touched a disk, and you could read every line you typed

  • Your answer came back with no disk in the way. The value sits in memory, and one lookup in the map costs about 27 billionths of a second on the machine that measured it.
  • You typed a line a person can read, and got a line a person can read. The whole conversation is one line in and one line out, which is why the real server can be driven from an ordinary terminal window with no special client.
  • When you got it wrong it said so, calmly, and carried on. The code that decided PING was not a command is the same code the real server runs, and it has 13 cases of its own in protocol/protocol_test.go.

A hundred thousand answers a second, on one desktop, measured seven times

These come from bench/RESULTS.md in this repository, which records the machine, the method and the wobble between runs next to every figure. The numbers below are from the harder of the two setups in that file, the one it calls the honest configuration.

107,783answers a second with 32 programs all reading at once Source: bench/RESULTS.md, cross-process table, measured 2026-07-27 on an AMD Ryzen 5 7600X3D, 6 cores and 12 threads, running Windows 11. Method: the server and the asking programs run separately on that one machine and talk over its loopback (the machine talking to itself). Each asker waits for its answer before asking again. Before the measuring

A note in store/store.go said that splitting the lock into pieces was not worth the complexity until a measurement showed the lock was busy. That was an opinion, written by the person who also wrote the lock.

After the measuring

The measurement exists now and says the lock is idle: under 0.4% of the time spent on an answer. The complicated version was not built, and the note in the file points at the numbers instead of at a hunch.

The tests that back this are in the repository and run in a few seconds: 15 test functions reporting 28 results, none of them failing, on 2026-07-27. Several of them open real connections to a real server and talk to it from eight programs at once.

It forgets everything the moment it stops

What this does not do

Written down here so nobody has to discover it later.

  • It never writes anything down. Stop the program and every label it held is gone. There is no save file and no way to reload one.
  • It holds only what fits in the machine's memory. Nothing is thrown out to make room, so a large enough pile of labels will run the machine out of memory.
  • It runs on one machine. There is no second copy keeping up, so if that machine goes away the answers go with it.
  • A label whose value is literally the text (nil) reads exactly like a label that was never set. That is the price of a protocol a person can read, and it is written down in the repository too.

Five files do the whole job

  1. cmd/kvstore/main.go starts the program, picks the port and stops it cleanly when you press Ctrl and C.
  2. server/server.go waits for programs to connect, and gives each one its own small worker so a slow visitor never blocks anyone else.
  3. protocol/protocol.go reads one line of text and decides what it means, or says clearly that it means nothing.
  4. store/store.go is the memory itself: labels pointing at values, with one lock so two writers never clash. This file and the one above it are what runs in your tab.
  5. bench/main.go is the measuring harness, and bench/RESULTS.md is what it found, caveats included.

The whole project is the Go standard library and nothing else. No downloaded packages.
